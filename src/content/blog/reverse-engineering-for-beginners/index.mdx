借助ai小白也能搞js逆向，本次逆向的目的是在仅通过node环境在不使用真实浏览器的情况下过datadome的盾，减少资源占用。大体思路就是拿到足够的正样本，然后模拟真实浏览器获得挑战并通过挑战，拿到cookie来复用，可以在node里复用也可以在curl_cffi里复用。


:::note
本文会借助ai写大部分的内容，同时我也会校对，写为一篇记录与ai边做边学的博客

:::

逆向 DataDome 时，有一个很容易让人提前庆祝的时刻：JavaScript 跑完了，请求也返回了 200，甚至拿到了新的 Cookie。

然后带着这个 Cookie 去请求正文，还是 401。

如果只把逆向理解成“把一段混淆代码还原出来”，这件事就很难解释。代码不是已经能跑了吗？字段不是已经生成了吗？究竟还有哪里不对？

这篇文章想借分析 Reuters 页面中 DataDome 客户端的经历，讲清楚这些问题。不是先摆一整章术语，再让你自己寻找它们的用途，而是沿着调查往前走：**遇到什么现象，为什么看这个位置，用到什么知识，最后能下什么结论。**

你只需要会读基本的 JavaScript，知道对象、数组、函数和 HTTP 请求是什么。不需要先背汇编指令，也不需要一开始就会写反编译器。

> 本文依据 2026 年 8 月至 10 月初的研究记录整理，不是一次新的在线复测。不同日期的脚本与挑战类型会变化，下文会把旧样本的结论标清楚。代码片段用于解释局部语义，不是 DataDome 原始源码，也不包含 Cookie、完整挑战请求或可复用的证明值。实际实验应在自有或获授权的环境中进行。

## 1. 面对几十万字节的代码，第一件事不是从头读

最初关心的问题很具体：浏览器提交给 DataDome 的动态字段，是怎么生成的？

在一个旧版 CAPTCHA 样本中，请求里有两个值得追踪的名字：`ddCaptchaEncodedPayload` 和 `plv3`。前者涉及行为数据等内容，后者在这个样本里来自环境检测相关的计算。这里只把它们作为该版本的定位线索，不把名字当作所有版本通用的协议定义。

如果直接打开 bundle，也就是打包后的大型 JavaScript 文件，从第一行读起，很快就会迷失：大量短变量名、嵌套函数、常量表和间接调用，几乎都在争夺注意力。

于是换一个方向：**不问整个文件在干什么，先问请求中的这个字段是谁写进去的。**

顺着请求组装的位置向前找，我们在旧样本中确认了这样的关系：

```text
请求中的 plv3
    ↑
window.plv3
    ↑
某个模块返回的对象 o.r
    ↑
模块内部的一段计算
```

这就是“从使用点反查定义”，也可以理解成最初级的逆向数据流分析。请求组装是输出端，赋值语句是连接线，而我们要沿着连接线找生产者。

其中一个赋值关系等价于：

```javascript
// 对已确认赋值关系的简化表达，不是完整生成逻辑。
window.plv3 = o.r
```

它看起来平平无奇，却把问题从“读懂整个网页”缩小到了“解释这个对象的 r 从哪里来”。

注意，这时我们**没有**证明 `r` 正确，更没有证明服务端会接受它。我们只找到了一段可追踪的来源关系。逆向中的很多进展，就是这样一点点缩小问题，而不是突然读懂所有东西。

## 2. HTML 很短，不代表逻辑不存在

接下来遇到的是一个看似无关、实际上很基础的问题：样本到底保存完整了吗？

早期容易把 HTML 当作程序本身。页面很短，没有熟悉的内联 VM，就怀疑服务端只给了一个终止页。但后续样本把逻辑拆到了外部 JavaScript：HTML 只是入口，真正的计算要等其他资源加载后才开始。

因此，分析对象不能只是“一个 HTML 文件”，而应是一个资源关系：

```text
页面响应
  → loader
  → 挑战页面或 iframe
  → 内联初始化脚本与外部脚本
  → 事件触发后的计算
  → 请求组装
```

这里顺带就遇到了浏览器的脚本执行模型。

对普通的外部 `defer` 脚本来说，下载可以与 HTML 解析并行，但执行要等待文档解析完成，并保持这类脚本之间的顺序；`DOMContentLoaded` 又与这些脚本的执行有关。这不是“把所有代码收集好，随便拼起来执行”就能等价替代的。

例如，前一段脚本可能只注册了事件监听器，后一段才设置输入。你提前派发事件，得到的就是另一条执行路径。把多个文件拼成一个文件，还可能改变源码位置和错误栈，而这些信息本身也可能被程序读取。

这一步学到的是：**程序的输入不只有函数参数，还有装载方式、执行顺序和事件发生的时机。**

我们因此把资源来源、脚本顺序、样本时间和文件 SHA-256 一起记录。哈希在这里不是用来“破解”的，而是给样本一个稳定身份证：只有确认字节相同，前后两轮结果才有资格直接比较。

## 3. 找到生成模块，却发现里面藏着另一门语言

继续进入旧样本的 `vm-obf.js`，看到的不是一串直接读取浏览器属性的代码，而是一个反复取出数字、查表、调用处理函数的循环。

把结构简化，大致是这样：

```javascript
// 解释器结构示意；不是 DataDome 的实际 opcode 或状态布局。
while (!state.halted) {
  const opcode = program[state.ip++]
  handlers[opcode](state)
}
```

这时才需要引入“虚拟机”这个概念。

这里的 VM 不是 VMware，也不是直接运行机器码的 CPU，而是作者用 JavaScript 写出来的一套小型解释器：

- `program` 保存自定义字节码；
- `ip` 是指令指针，表示下一步从哪里读；
- `opcode` 是操作编号；
- `handler` 负责解释这个编号对应的操作；
- `state` 保存栈、临时值、调用帧和结束状态。

浏览器认识的是外层 JavaScript；真正需要研究的逻辑，又被编码成内层的另一套指令。

普通混淆可能只是把变量改名、把字符串藏起来；这种虚拟化混淆则把“读属性”“相加”“判断”“调用函数”重新编码了一遍。即使格式化了外层源码，内层程序也不会自动变得可读。

所以研究任务自然分成两层：

**先恢复指令的含义，再理解这些指令组成的程序。**

这就像先知道每个汉字怎么读，再理解一篇文章。认识所有字，并不等于理解文章在说什么。

## 4. 找到 103 个 handler，为什么还不算读懂程序？

分析vm的话只能靠ai了。

2026 年 8 月 9 日那个旧样本里，研究记录确认了 103 种有效 opcode handler。这个数字只属于那个样本，不是 DataDome 的固定规格。

怎样判断一个 handler 在干什么？不要先猜名字，先看它执行前后修改了哪些状态。

例如，下列教学示意完成的是“弹出两个值，相加，再压回去”：

```javascript
// 教学用的最小状态转移。
const stack = [3, 5]
const right = stack.pop()
const left = stack.pop()
stack.push(left + right)
console.assert(stack.length === 1 && stack[0] === 8)
```

在真正的 handler 中，变量名可能不可读，栈也可能只是一块数组加一个指针，但状态变化仍然可以观察。再换一组输入，就可以继续检查它是数字相加、字符串拼接，还是别的转换。

同理，如果一段 handler 根据条件修改 `ip`，它就可能实现条件跳转。把所有可能的后继位置连起来，就是控制流图，也就是 CFG。

**控制流回答“下一步去哪”，数据流回答“这个值从哪来”。** 两者要结合起来看：你不仅要知道某个分支被执行，还要知道是什么输入决定它被执行。

那为什么 103 个 handler 都标注了，程序还没有读懂？因为指令语义只是局部规则。一个“读属性”指令可以读取几百种不同属性，一个“调用函数”指令也可以调用完全不同的函数。真正的含义还取决于运行到这里时，栈里装的是什么。

还有一个容易踩的坑：字节码里的某个标记字节，不一定只出现在指令边界。旧样本中有 169 个字节与 handler 标记相同，但经过长度、边界与结构验证，只有 103 个是有效记录。

这也是文件格式分析里的常识：**搜索命中只是候选，结构验证才是证据。**

## 5. “缺什么补什么”为什么把程序带进了错误分支？

识别出解释器之后，一个自然想法是：把它放进 Node，缺哪个浏览器对象，就补哪个。

最方便的做法，是写一个万能占位对象。任何属性访问都返回另一个对象或函数，任何调用都“不报错”。这类占位实现通常叫 stub；如果借助 JavaScript `Proxy` 拦截访问，还能把缺失项记录下来。

问题是：程序不只关心“有没有报错”，还关心值的类型与语义。

8 月旧样本的固定 stub 路径执行了部分指令，但没有正常到达结束标志。记录显示，一些本来参与数值运算的属性读取拿到了占位函数，类型转换之后进入了错误分支，异常又被 VM 自己捕获了。

为什么一个函数也能参加位运算？看看这个可独立运行的小例子：

```javascript
const stub = () => 123

console.assert(typeof stub === 'function')
console.assert(Number.isNaN(Number(stub)))
console.assert((stub & 255) === 0)
console.assert(undefined >>> 0 === 0)
```

`Number(stub)` 不会替你调用函数取得 123。对这里这个普通函数，它会经过原始值转换，最终得到 `NaN`；而按位运算又会执行整数转换。

于是，占位函数不仅没表达真实环境，还悄悄变成了一个足以改变分支的数值。

后来把 `window`、`document`、`navigator`、`screen` 等根对象分开，并保持派生对象身份一致，合成路径才推进到正常结束。这一步带来的不是“已经模拟了浏览器”，而是更窄的结论：**某些对象与类型关系会影响程序能否走到末端。**

所谓环境建模，不是把属性名填满，而是还原程序实际依赖的行为：返回什么类型、是不是同一个对象、什么时候抛异常、异步结果什么时候可见。

另外，Node 的 `vm` context 只是执行上下文，不是安全隔离边界。Node 官方明确指出 `node:vm` 不是安全机制。运行外来脚本仍需要独立、受限的执行环境，不能把宿主文件、网络能力和凭据暴露给它。

## 6. 程序终于返回字符串，差异却在编码之前

让解释器正常结束之后，又出现了一个很诱人的假终点：`r` 终于是字符串了。

但在同一个 8 月旧样本的对照中，合成路径的字符串长度是 1,391，而浏览器样本是 407。这里的数字只是帮助理解当时的差异，不能拿来作为新版字段长度的要求。

接下来该怎么查？继续乱补 API，还是从最终输出往回找？

我们已经知道末端大致经过这样的过程：

```text
数组元素
  → join("")
  → btoa
  → 字符替换
  → 返回字符串
```

于是把观察点放在 `join` 之前。

旧样本中的浏览器路径，有一个长度为 306 的数组，写进去的是单字符字符串；对应的合成路径，数组长度是 149，元素却主要被归类为 `function`。

这比“最终字段长度不同”有用得多。它说明至少存在明确的上游输入形状差异：你不能指望把 149 个占位函数交给相同的编码函数，就得到 306 个真实字符组成的结果。

这里用到的方法叫**从输出向后切片**：不是追踪所有变量，而是只追踪最终输出依赖的那一部分。

更细一点，怎样确认某次数组写入来自刚刚的函数返回值？需要关联调用、返回和写入，并记录数组对象身份、索引、值类型与发生顺序。这条可复查的来源链，就是 provenance，也就是数据来源追踪。

公开记录往往不需要写出字符原值。仅仅知道“同一个数组”“数字索引”“单字符字符串”“与上一调用返回值对应”，就足以排除不少错误解释。

这也解释了为什么逆向不是“看到 Base64，解一下就结束”。Base64 是表示方式，不是生成材料的算法，更不是自动成立的加密保护。

## 7. 把算法翻译成 Python，最先出错的可能是一个字符

随着末端编码和部分哈希结构被识别，一个新的工作出现了：用独立代码复算中间结果。

独立实现很重要。如果仍然调用原来的混淆函数，就只能证明“它又运行了一次”，不能证明我们已经理解并复现了它的规则。

但从 JavaScript 翻译到 Python 时，照着公式抄还不够。

例如，9 月一些固定样本中的 cyrb53 路径涉及 `charCodeAt` 与 `Math.imul`。前者读取 UTF-16 码元，后者按 32 位整数乘法取结果。它们并不等于“Python 遍历字符，再做普通乘法”。

先只看字符串：

```javascript
const text = '😀'
console.assert(text.length === 2)
console.assert(text.charCodeAt(0) === 0xd83d)
console.assert(text.charCodeAt(1) === 0xde00)
```

这个字符在 JavaScript 中占两个 UTF-16 码元。如果 Python 实现需要模拟 `charCodeAt`，可以先显式取得码元：

```python
text = '😀'
encoded = text.encode('utf-16-le', errors='surrogatepass')
units = [
    int.from_bytes(encoded[i:i + 2], 'little')
    for i in range(0, len(encoded), 2)
]
assert units == [0xD83D, 0xDE00]
```

再看整数：

```javascript
console.assert(Math.imul(0xffffffff, 5) === -5)
console.assert(Math.imul(0xffffffff, 5) >>> 0 === 4294967291)
```

同一组低 32 位比特，可以按有符号或无符号整数解释。Python 整数不会自动以同样方式截断，所以复算时必须明确位宽、截断点和符号。

还有 `btoa`：它接收的是每个字符都能表示一个字节的“二进制字符串”，并不自动把任意 Unicode 文本转成 UTF-8。看到它时，必须继续确认上游到底组装了什么。

这些细节听起来像语言基础，却往往决定“数学公式看起来一样”的两份实现为什么对不上。

另外，**识别到一个熟悉的哈希，不代表整个字段都是这个哈希，也不代表新版仍然使用同一算法。** 我们在后续脚本里还遇到过不同的哈希路径。算法名称、常量和指令位置，都要跟具体样本绑定。

## 8. 没有出现在日志里的调用，真的没有执行吗？

9 月的一次追踪里，日志没有显示预期的 cyrb53 起始调用。如果急着解释，很容易写出“这一分支没有走到”。

后来发现，日志只保留了尾部。调用发生过，只是早期记录已经被丢掉了。

这个坑的价值不比一个算法发现低，因为它提醒我们：**分析工具也是实验的一部分，也会制造盲区。**

因此，一份 trace 至少要说明：

| 记录项   | 要回答的问题                     |
| -------- | -------------------------------- |
| total    | 一共观察到了多少事件？           |
| retained | 最终保留了多少条？               |
| dropped  | 因容量限制丢了多少条？           |
| thrown   | 被观察的调用中有多少抛出了异常？ |

具体计数口径必须由工具定义清楚。例如，异常是否也会占一条 retained 记录，不能靠猜。

即使 `dropped` 为零，也要检查观测覆盖范围：钩子什么时候装上，观察了哪些调用点，是否跨异步任务，记录窗口从哪里开始。完整的局部窗口不等于完整的全程序轨迹。

后来的做法是缩小观察范围，只追相关指令窗口与指定状态槽。不要一边让全量日志溢出，一边拿截断结果讲完整故事。

插桩还可能改变被测程序本身。源码重写、函数包装、额外计时都会影响执行；如果程序观察源码或调用栈，影响尤其明显。因此要保留未插桩基线，对照插桩前后的输出和行为。

一个靠谱的结论，不仅要解释程序，还要解释：**为什么这份观察值得相信。**

## 9. 改了时区，哈希变了，最终字段没变，说明什么？

理解数据流之后，我们开始做反事实实验：固定其他条件，只改变一个输入，看看输出如何变化。

9 月 27 日的一组固定样本实验中，改变时区相关条件后，一组中间哈希发生了变化，但最终 `plv3` 没变。

最省事的解释是：“这组哈希没用。”

但继续追踪，发现它确实被读取过，而且有多个消费点。已追到的一条局部路径，还经过取低位和表操作。**输出没变，不等于中间值没被使用。**

可能的原因很多：

- 差异被截断或掩码抹掉了；
- 两个不同索引最终取到了相同结果；
- 中间写入后来被覆盖；
- 变化影响了另一段输出，而不是当前观察的字段；
- 这次实验没有覆盖真正敏感的条件。

这些只是候选解释，不能从一个不变的结果里挑一个自己喜欢的当答案。当时只完成了部分消费路径的局部追踪，不能把剩余读取全部判为噪声。

这就是相关性与因果关系的区别。一个值变化，说明它对改动敏感；想证明它如何影响最终结果，还得把中间路径追完整。

实际对照也应先重复同条件基线，再改变一个因素，最后恢复基线。否则时间、随机源或挑战本身的变化，都可能被误记到那个被修改的变量头上。

## 10. 为什么浏览器里有，Node 里也有，结果仍然不同？

到这里，很容易把剩下的问题理解为“还有几个 API 没补”。实际情况比一份属性清单复杂得多。

### 对象相同，不是看起来相同

同一个对象的重复读取，和每次创建一个内容相同的新对象，不是一回事：

```javascript
console.assert({ width: 100 } !== { width: 100 })
```

跨 iframe 又涉及不同的 JavaScript realm：各自的全局对象、构造器和原型身份会影响比较结果。把所有 iframe 都指向同一个全局对象，并不是一个无害的简化。

### 没有权限，也是一种真实行为

某次跨站挑战帧的实测中，存储访问会受到限制。若模型为了“完善”而让它总能成功，就模拟出了一个与被测浏览器不同的世界。

同样，真实环境没有提供的高熵浏览器版本、系统信息或硬件值，不应该因为代码里有位置可以填，就随便补进去。缺失、异常、不可用，都可能是需要忠实表达的行为。

这些现象取决于浏览器版本、权限与页面上下文，不是说某个 API 在所有浏览器里都应被关闭。

### 异步顺序，也是程序输入

有的检测先发起异步任务，稍后才收集结果。如果合成调度器一口气处理完全部定时器，或者过早执行编码回调，就可能在结果尚未写入时打包字段。

一个不涉及 DataDome 的小例子，可以帮助理解同步代码、微任务与定时器的先后关系：

```javascript
const events = []
setTimeout(() => {
  events.push('timer')
  console.assert(events.join(',') === 'sync,microtask,timer')
}, 0)
Promise.resolve().then(() => events.push('microtask'))
events.push('sync')
```

但这个例子不是完整的浏览器调度模型。真实页面还涉及渲染、I/O 和不同任务来源。它只说明一件事：**值最后能算出来，不代表它在被读取时已经存在。**

因此，“补环境”真正要做的是语义建模，而不是制造一个永远不报错的万能对象。

## 11. 最后的 401，把问题从 JavaScript 拉回 HTTP

现在回到开头：为什么已经有字符串、200 和 Cookie，正文仍然失败？

因为这几件事处在不同层级。

JavaScript 生成的是要提交的材料；Cookie 是服务端在交互后返回的。Node 并不是算完一个函数，就自行签发了一张服务端必然认可的通行证。

在项目里，我们要求候选 Cookie 再经过三类真实页面验证：Reuters 首页、栏目页、文章页。所谓严格 `3/3`，不是三次任意 200，而是三类页面都确认为正常文档，不是挑战页、空壳或错误页面。这是本项目的验收规则，不是 DataDome 官方协议。

对应的证据链是：

```text
当轮新挑战与对应资源
  → 独立计算本轮材料
  → 原 HTTP 会话提交
  → 取得候选 Cookie
  → 三类真实文档验证
  → 实际使用端再次验证复用
```

10 月 2 日的一批记录里，生成端已经能通过 `3/3`，但交给 worker 后却只有 `1/3`。此时再盲目钻进 VM 里改算法，就很可能在排查错误的层级。

于是实验改成对照 Session。这里的 Session 不只是 Cookie，它还包含客户端配置、请求上下文、连接与其他状态。

两枚独立候选都曾在复制生成端完整配置与应用层状态的新 Session 中通过 `3/3`；移除项目里的请求上下文包装器后，则都出现三个 401，而原 Session 复测仍为 `3/3`。

这支持“请求上下文组合会影响所测结果”，但不支持“已经定位某一个请求头”。因为那个包装器同时管理多项行为，实验也没有固定所有网络变量。其中一轮后置完整新 Session 对照还有传输错误，不能把它润色成全部成功。

它还否定了另一个过强判断：成功复用并不必然要求保留原 TCP 连接。新 Session 在所测条件下也可以成功。

这就是消融实验：从已能工作的完整条件里移除一个组件，观察差异。它帮助定位范围，但组件里如果还包含多个因素，就需要继续拆分，而不是提前宣判唯一原因。

同样，代理的 CONNECT 200 只说明建立隧道这一层的结果；浏览器出现 request 事件，也只说明启动了请求流程。它们都不能自动替代目标站响应，更不能替代真实正文验收。

## 12. 做到哪里，才可以说“成功”？

把这段经历连起来，能看到好几个不同的终点：

- 找到 `plv3` 的赋值位置，完成的是字段定位；
- 标注 VM 指令，完成的是解释器局部语义；
- 到达 halt，说明某条执行路径结束；
- 独立复算编码，证明对应子过程被理解；
- 浏览器正样本，说明那组条件下存在可接受路径；
- 独立新挑战通过真实文档验证，才支持对应路线的接受结论；
- 实际使用端可以复用，又是额外的工程验证。

这不是故意把成功标准抬高，而是避免用一个层级的证据回答另一个层级的问题。

截至本文采用的 10 月 2 日记录，已经有两次独立 Node 运行在服务端当次提供的 **interstitial 设备检查路线**上完成 fresh `3/3`；输入没有使用浏览器产出的 Cookie、证明值或运行时快照。之后还发生了上文提到的移交与生产接入排查。

但这不等于同一时期的滑块路线已经被验证通过，也不等于 8 月旧 VM 的所有未知点都被补齐。早期旧版滑块的成功、后来的设备检查成功，是不同版本和路线的证据，不能合并成“DataDome 已经全部逆向完成”。

这里有个重要区别：**用 Node 执行原始脚本并建模所需环境，和把整个算法独立重写，是两种不同成果。** 前者的服务端成功，不能替代后者尚未完成的数据流解释。

## 如果从头再做一次，我会怎样开始？

我不会先要求自己学完所有 VM、浏览器和密码学知识。第一轮只拿一个固定样本，完成一条尽可能短、能复查的来源链：

1. 先确认资源完整，区分挑战路线，记下样本时间与哈希。
2. 从某个输出字段反查写入点，不从整个 bundle 的第一行开始读。
3. 碰到分派循环，再补学 opcode、栈、调用帧和控制流。
4. 执行卡住时，检查真实值的类型与使用方式，不靠万能 stub 消灭异常。
5. 对照输出前的数组、字符和编码步骤，逐段缩小差异。
6. 需要跨语言复算时，再认真处理 UTF-16、位宽和类型转换。
7. 每次解释缺失日志之前，先确认自己的观察没有截断或漏装。
8. 把离线算法结论、浏览器对照、服务端接受和实际复用分开记录。

DataDome 只是这次的案例。真正可以带走的方法，是把一个巨大的“为什么不行”，拆成一串可以验证的小问题。

**逆向的进步，不是你给多少变量起了名字，而是有多少句“可能是这样”，已经变成“在这些条件下，我能证明它是这样”。**
